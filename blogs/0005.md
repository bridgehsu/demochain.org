对，产品入口分成**查询代币**和**买入代币**。下面把两个入口展开成可落地的程序流程；不单独设置策略判断步骤，买入前只执行必要的参数、报价和交易检查。

## 入口一：查询代币

### 1. 接收合约地址

机器人提供“查询代币”按钮。用户点击后发送地址，机器人将会话状态设为 `WAITING_FOR_TOKEN_ADDRESS`，并保存 Telegram 用户 ID、会话 ID 和超时时间。

### 2. 校验地址格式

1. 去掉地址首尾空格。
2. 检查是否为空、长度是否过长。
3. 尝试用 EVM、Solana、TRON 地址解析器识别格式。
4. 如果全部解析失败，回复具体错误，并保持等待地址状态，允许用户重新输入。
5. 如果是 EVM 地址，将候选链标记为 Ethereum、Base、BNB；不能仅凭格式确定具体是哪条链。

### 3. 确定公链

- 用户已选择公链：只在该链查询。
- 用户未选择公链：
  1. 按地址格式列出候选链。
  2. 在候选链上并行查询该地址。
  3. 将查询成功且能识别代币信息的链展示为按钮。
  4. 用户选择后，将链 ID 和标准化地址保存到当前会话。
- RPC 超时或不可用时，返回“暂时无法查询”，提供重试。
- 多条候选链都存在该地址时，分别展示结果，要求用户选择。

### 4. 查询代币信息

1. 根据所选链调用对应 RPC。
2. 确认地址对应的链上对象符合代币标准。
3. 读取名称、符号、精度及代币地址。
4. Solana 还需要确认其为支持的 Token Program 下的 Mint；名称和符号按支持的 Metadata 规范读取。
5. 字段读取失败时显示“未知”或“读取失败”，不能用默认值填充。
6. 将链 ID 和代币地址作为代币唯一标识，名称、符号仅用于展示。

### 5. 查询市场信息

1. 加载该链已接入的 DEX 配置。
2. 查询目标代币对应的交易池。
3. 读取池子所属 DEX、交易对和链上流动性状态。
4. 获取参考价格和近期成交数据（如果已接入相应数据源）。
5. 没有池子时也展示代币信息，并标明“暂未发现已接入 DEX 的交易池”。
6. 标记行情数据的来源和更新时间；此处价格是参考行情，不是指定金额的可执行报价。

### 6. 返回查询结果

机器人展示：

- 公链、代币名称、符号、精度和合约地址
- 已发现的 DEX、交易池和交易对
- 流动性及参考价格（如果可获取）
- 数据来源和更新时间
- “买入”按钮、“重新查询”按钮

查询结果可暂存在会话或缓存中，但买入时要重新读取实时状态和报价。

## 入口二：买入代币

### 1. 进入买入流程

用户从查询结果点击“买入”。机器人从当前会话读取链 ID、代币地址和钱包信息；如果会话数据已过期，则提示用户重新查询代币。

### 2. 选择支付资产和金额

1. 展示该链支持的支付资产。
2. 用户选择支付资产。
3. 展示预设金额按钮，并允许用户输入自定义金额。
4. 校验金额是有效正数、精度没有超过支付资产精度，且没有超过产品设定的单笔上限。
5. 保存支付资产和金额。

### 3. 获取本次交易报价

1. 重新读取目标代币和支付资产的交易池状态。
2. 查询直接交易路径；没有直接池时，再按产品配置查询允许的多跳路径。
3. 对候选路径调用对应 DEX 的 Quoter 或报价方法。
4. 获取预计到账量、路径、池子、DEX 费用和报价区块。
5. 估算网络费，并对选定的 Router 调用进行只读模拟。
6. 如果无可用路径、流动性不足或模拟失败，向用户返回原因并停止。
7. 记录报价时间及有效期限。

### 4. 展示交易确认信息

展示：

- 支付资产和买入金额
- 目标代币和预计到账量
- 最小到账量和最大滑点
- DEX、交易路径和 DEX 费用
- 预估网络费
- 报价时间和有效期

提供“确认买入”和“取消”按钮。报价过期后，用户需要重新获取报价并查看更新后的交易信息。

### 5. 检查钱包、余额和授权

用户点击确认后：

1. 检查钱包地址是否已连接。
2. 检查钱包当前网络是否与本次报价的公链一致。
3. 查询支付资产余额和原生币余额，确认足够支付买入金额和网络费。
4. 检查支付资产对 DEX Router 的授权额度。
5. 如果授权不足，先构造授权交易，请用户单独确认和签名；授权完成后重新检查余额、报价和模拟结果。
6. 若缺少钱包连接或余额不足，说明原因并返回相应步骤。

### 6. 构造并发送买入交易

1. 按已选 DEX 和报价路径构造交易。
2. 设置支付金额、最小到账量、接收钱包地址和截止时间。
3. 再次执行只读模拟；失败则不发送。
4. 将交易交给用户钱包签名。
5. 用户拒绝签名时记录为 `REJECTED_BY_USER`。
6. 签名成功后广播交易，取得交易哈希。
7. 保存交易哈希，状态设为 `SUBMITTED`，回复“交易已提交，等待链上确认”。

### 7. 跟踪交易结果

1. 根据交易哈希查询交易收据。
2. 尚未打包时标记 `PENDING`，继续轮询或订阅链上状态。
3. 收据执行失败时标记 `FAILED`，保存失败原因和已产生的网络费。
4. 收据执行成功后等待产品设定的确认条件。
5. 达到确认条件后读取实际到账量、实际支付量和实际网络费，标记 `CONFIRMED_SUCCESS`。
6. 长时间未确认时标记 `TIMEOUT_PENDING` 并继续跟踪。超时不等于失败。

### 8. 发送通知

- `CONFIRMED_SUCCESS`：发送成功消息，包含实际到账量、交易哈希和区块浏览器链接。
- `FAILED`：发送失败消息、失败原因及交易哈希（若已广播）。
- `PENDING`：发送处理中状态，不报告成功或失败。
- `TIMEOUT_PENDING`：告知仍在确认，并继续后台跟踪。
- 通知失败可以重试，但重试只发送消息，不能重新发起买入。

### 9. 保存买入记录

每次买入保存：

- 请求 ID、Telegram 用户 ID、钱包地址
- 公链、代币地址、支付资产和买入金额
- 报价、路由、交易池、报价时间和区块号
- 用户确认时间、授权交易哈希（如有）
- 买入交易哈希和状态变化
- 实际到账量、实际费用和失败原因
- 通知渠道、发送时间和发送结果
